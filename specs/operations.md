## 方針

- **自律**：計画から改善まで、AIが判断して進める。オーナーの承認を待たない
- **本番への公開**：人が決める。テストの環境で確かめてから、任意のときに出す
- **記憶に頼らない**：AIはセッションをまたいで記憶を持たない。判断に必要な情報はすべてリポジトリに書く
- **仕様が先**：系統と仕様にないことは、先に仕様を決めてから作る
- **作る役と確かめる役を分ける**：作ったセッションとは別のセッションが確かめる
- **小さく出す**：1つのPRは1つの変更にする。大きい変更は重ねたPRにする
- **常にリリース可能**：main は、いつ本番に出してもよい状態に保つ

## 正とする情報

- **一次資料**：[courses-of-study](https://github.com/goataka/courses-of-study)。学習指導要領、解説、評価規準の転記
- **何を学ぶか**：[学習の系統](../curriculum/README.md)
- **どう作るか**：この仕様。アプリの決まり、表記、合格の基準、ヒント、運用
- **何をするか**：GitHub の Issue。作業の一覧と状態
- **なぜそうしたか**：[決定の記録](decisions/README.md)。仕様を変えた理由と、選ばなかった案
- **エージェントへの指示**：[AGENTS.md](../AGENTS.md) とスキル。仕様の中身は書かず、仕様への参照だけを書く

## 役割

役割ごとに、別のセッションとして動かす。

- **計画**：対応表と Issue の状態から次の作業を決め、Issue にする
  - 頻度：週1回
  - 基準：[目標とコースの対応表](courses/README.md)の優先度、未解決の不具合、監視で見つかった問題の順
- **作成**：準備のできた Issue を1つ取り、仕様に沿って変更し、PR を出す
  - 頻度：作業がある間、1件ずつ
- **レビュー**：PR を、系統と仕様に照らして確かめる
  - 観点：系統の目標と範囲に合うか、子ども向けの表記と内容が正しいか、仕様の決まりを守っているか
  - 結果：承認するか、直す点をコメントする。作成の役が直す
- **リリース**：品質ゲートとレビューを通った PR をマージし、公開を確かめる
- **監視**：本番、依存関係、一次資料の変化を確かめ、問題を Issue にする
  - 頻度：毎日
- **改善**：監視の結果やレビューで多い指摘から、仕様や系統の直し方を Issue にする
  - 頻度：月1回

## 流れ

1. **計画**：Issue を作り、準備ができたものに印を付ける
2. **作成**：ブランチを作り、変更して PR を出す
3. **自動検証**：品質ゲートを CI で実行する
4. **レビュー**：レビューの役が確かめる。直す点があれば2に戻る
5. **マージ**：自動マージで main に入れる
6. **テストの環境**：main への反映で、テストの環境に公開する
7. **リリース**：人が、main から release への PR をマージして本番に出す
8. **公開後の確認**：本番で動作を確かめる。失敗したら戻す
9. **監視と改善**：見つかった問題を1に戻す

## 作業の管理

- **作業の単位**：Issue 1件を PR 1件か、重ねた PR の1組にする
  - 例：1つのコースの追加、1つの不具合の修正、1つの仕様の変更
- **ラベル**
  - 種類：`content`、`app`、`fix`、`ops`、`spec`
  - 状態：`ready`、`in-progress`、`blocked`、`needs-owner`
- **同時に進める数**：作成中の作業は1件、開いている PR は1組までにする
  - 理由：重ねた PR の衝突と、レビュー待ちの滞留を防ぐ
- **完了**：PR のマージで Issue を閉じる。対応表のコースの列と、系統の「コース」を同じ PR で更新する

## 品質ゲート

マージの前に、すべてを CI で自動実行する。
どれか1つでも失敗したらマージしない。

- **書き方**：Markdown、コード、ワークフローの Lint と整形、秘密情報の検出
- **型**：型の検査
- **系統**：前提の ID の存在、学年の順、循環、学習指導要領の項目の網羅
- **仕様**：対応表とコースの一致、表記の決まり、合格の基準の値
- **問題**：出題する問題の答えが正しいこと、問題が目標の範囲と内容の取扱いに収まること
- **画面**：E2E テスト、アクセシビリティの検査、タブレットとスマートフォンの表示
- **大きさ**：ページの読み込みの大きさが上限を超えないこと
- **レビュー**：レビューの役の承認

## リリースと戻し

- **公開先**：GitHub Pages。テストの環境との分け方は[環境](environments.md)に従う
- **公開の契機**：テストの環境は main への反映。本番は release への反映
- **公開後の確認**：本番の URL で、各アプリの開始から1回の練習の終了までを確かめる
- **戻し**：公開後の確認に失敗したら、原因の PR を戻す PR を作り、品質ゲートを通してマージする
- **学習記録**：端末に保存した学習記録の形を変えるときは、古い形から読み替える処理を同じ PR に入れる。読み替えできない変更はしない

## 監視と改善

- **本番**：公開後の確認と同じ内容を毎日実行する
- **依存関係**：更新と脆弱性を確かめ、更新の PR を作る
- **一次資料**：courses-of-study の変更を確かめ、系統に影響するものを Issue にする
- **改善の材料**：品質ゲートの失敗、レビューの指摘、監視の結果
  - 利用者の学習データは集めない。改善は、仕様と系統への適合で判断する

## 安全

- **子どもの情報**：個人情報を扱わない。学習記録は端末の中だけに置き、外部に送らない
- **外部サービス**：アプリから外部サービスを呼ばない。広告と計測を入れない
- **内容**：子ども向けにふさわしくない表現を入れない。レビューの観点に含める
- **権限**：ワークフローとエージェントには、必要な権限だけを与える
- **上限**：1日に作る PR の数に上限を設け、超えたら翌日に回す
- **停止**：リポジトリの変数で、すべての自動作業を止められるようにする

## オーナーの関与

次のときだけ、Issue に `needs-owner` を付けて止める。
ほかはすべてAIが判断する。

- **費用**：有料のサービスや、費用の増える設定が必要なとき
- **権限**：リポジトリの設定や、新しい権限が必要なとき
- **公開範囲**：対象とする学年や教科を広げるか狭めるか
- **法令**：著作権や個人情報に関わる判断
