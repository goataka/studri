## 方針

- **同じビルド**：テストは、本番に公開するものと同じビルドの成果物で行う
- **使い捨て**：自動のテストの環境は、検証のたびに作って消す
- **人間用のテストの環境**：main の中身を常に公開し、本番に出す前に人が触って確かめられるようにする
- **本番は読むだけ**：本番での確認は、ページを開いて操作するだけにする。本番の設定やデータを変えない

## 環境の一覧

- **ローカル**
  - 場所：作成の役のセッションの中
  - 使い方：ビルドした `dist/` をローカルのサーバーで配信し、品質ゲートを実行する
- **PR のテスト**
  - 場所：GitHub Actions の実行の中
  - 使い方：PR ごとにビルドし、`dist/` を配信して品質ゲートを実行する
  - 残すもの：`dist/` と画面の画像を、実行の成果物として残す。レビューの役はこれを見て確かめる
- **テストの環境**
  - 場所：GitHub Pages の `/staging/`
  - 公開：main への反映のたび。`/staging/` だけを置き換える
  - 環境名：`staging`。画面の上に「テストの環境」の帯を出し、検索に載せない
- **本番**
  - 場所：GitHub Pages の `/staging/` 以外
  - 公開：release ブランチへの反映のときだけ。`/staging/` 以外を置き換える
  - 環境名：`production`
  - 確認：公開の直後と毎日、本番の URL で E2E の確認を実行する

## 公開のしくみ

- **公開元**：gh-pages ブランチ。Pages はこのブランチの中身をそのまま公開する
- **一部の置き換え**：公開のワークフローが、環境ごとに自分の場所だけを書き換える。もう一方の環境は残る
- **リリース**：人が任意のときに、main から release への PR をマージする
- **初回**：release を作って一度公開してから、Pages の公開元を gh-pages に切り替える

## 環境の違い

- **ビルド**：すべての環境で同じコマンドを使う
- **公開先のパスと環境名**：環境ごとに変えるのは、この2つだけにする。ビルドの設定で渡す
- **環境名で変わる表示**：テストの環境の帯と、検索に載せない指定だけ。ビルドが html に入れる
- **環境名**：`develop`、`staging`、`production`。指定がないときは `develop`
- **テスト用の処理**：アプリにテストのための分岐を入れない。テストはブラウザーの操作だけで行う
- **バージョン**：ビルドしたときの時刻を、フッターのバージョンに入れる。どの環境でも同じ形にする
- **画像の比較の基準**：PR のテストの環境で撮る。フォントが環境ごとに違い、ほかの環境の画像とは一致しないため

## データの分離

- **学習記録**：ブラウザーの localStorage にだけある
- **保存名**：`<環境名>:<アプリの保存名>` にする。同じドメインに複数の環境を置いても、記録が混ざらない
- **前の記録**：環境名を付ける前の本番の記録は、本番でだけ写して引き継ぐ。元の記録は消さない
- **テスト**：毎回新しいブラウザーの状態で始め、終わったら消す
- **本番の確認**：確認用のブラウザーの状態は毎回新しくし、実際の利用者の記録には触れない
- **秘密情報**：アプリには秘密情報がない。環境ごとの秘密情報も持たない

## 選ばなかった案

- **別のリポジトリのテストの環境**：同じドメインになり、分ける利点が少ない。本番に書き込めるトークンを別の場所に置くことになる
- **毎回サイト全体を公開**：テストの環境を更新するたびに、本番も作り直すことになる
- **PR ごとのプレビューの公開**：PR ごとの場所の作成と片付けが要る。実行の成果物とローカルの配信で、確認に必要なことは足りる
